# Best Practices

This guide covers best practices for creating high-quality, maintainable CyanPrint templates.

## Template Design Principles

### 1. Single Responsibility

Each template should do one thing well:

import { Tab, Tabs } from 'fumadocs-ui/components/tabs';

| Good | Avoid |
| ---- | ----- |
| React component template | React + Vue + Angular template |
| Node.js API template | Node.js + Python + Go API template |
| Docker configuration template | Full DevOps pipeline template |

### 2. Composability

Design templates to work together:

```json
// Instead of a monolithic template:
{
  "name": "fullstack-monolith",
  // Contains: frontend + backend + database + deployment
}

// Prefer composable templates:
{
  "name": "fullstack-app",
  "children": [
    { "name": "frontend", "template": "@org/react-template" },
    { "name": "backend", "template": "@org/node-api-template" },
    { "name": "database", "template": "@org/postgres-template" }
  ]
}
```

### 3. Convention over Configuration

Provide sensible defaults:

### Validate Input Early

```ts
const projectName = await cyan.inquirer.text({
  message: 'Project name:',
  validate: (value) => {
    if (!value.trim()) return 'Project name is required';
    if (!/^[a-z0-9-]+$/.test(value)) {
      return 'Project name must be lowercase alphanumeric with dashes only';
    }
    if (value.length > 100) {
      return 'Project name must be less than 100 characters';
    }
    if (value.startsWith('-') || value.endsWith('-')) {
      return 'Project name cannot start or end with a dash';
    }
    return true;
  }
});
```

## File Organization

### Template Directory Structure

```
my-template/
├── cyanprint.json           # Configuration
├── README.md                # Documentation
├── template/
│   ├── index.ts             # Entry point
│   ├── helpers/             # Helper functions
│   │   ├── validators.ts
│   │   └── generators.ts
│   └── files/               # Template files
│       ├── base/            # Always included
│       ├── typescript/      # Conditional
│       └── testing/         # Optional
└── tests/
    ├── template.test.ts
    └── fixtures/
```

```ts
async execute(cyan: Cyan): Promise<void> {
  const features = cyan.answers.features as string[];

  // Always include base files
  const baseFiles = cyan.glob('template/files/base/**/*');

  // Conditionally include feature files
  const featureFiles = [];
  if (features.includes('typescript')) {
    featureFiles.push(...cyan.glob('template/files/typescript/**/*'));
  }
  if (features.includes('testing')) {
    featureFiles.push(...cyan.glob('template/files/testing/**/*'));
  }

  // Process all files
  for (const file of [...baseFiles, ...featureFiles]) {
    await this.processFile(cyan, file);
  }
}
```

```ts
private async processFiles(cyan: Cyan, files: string[]): Promise<void> {
  for (const file of files) {
    // Calculate output path relative to template root
    const outputPath = file.replace('template/files/', '');

    // Skip files that don't match current configuration
    if (this.shouldSkipFile(file, cyan.answers)) {
      continue;
    }

    // Apply processor transformation
    await cyan.processors.run('default-processor', {
      input: file,
      output: outputPath
    });
  }
}
```

## Versioning

### Semantic Versioning

Follow [SemVer](https://semver.org/):

- **MAJOR** (1.0.0 → 2.0.0): Breaking changes to template output or API
- **MINOR** (1.0.0 → 1.1.0): New features, backward-compatible
- **PATCH** (1.0.0 → 1.0.1): Bug fixes

### Breaking Changes

Document breaking changes in CHANGELOG.md:

```markdown
# Changelog

## 2.0.0

### Breaking Changes
- Removed `redux` option (use `stateManagement: 'redux'` instead)
- Changed output directory structure

### Features
- Added support for state management selection

### Fixes
- Fixed TypeScript configuration for strict mode
```
